# Programmatic / code-driven motion graphics and 3D for explainer videos (state of the art 2025–2026), and feasibility in a CPU-only container

Scope reminder: target is a 90 s, 1080×1920, 30 fps (2,700 frames) explainer on placebo in endodontics, rendered in a CPU-only Linux container (4 cores, 15 GB RAM, headless Chromium + Playwright with SwiftShader WebGL, ffmpeg 6.1, Node 22, Python 3.12/3.13, uv, npm/PyPI reachable, GitHub release downloads blocked). Research date 2026-11-25. Items marked UNVERIFIED come from general practitioner knowledge, not a source fetched in this session.

## Q1. Code-driven animation frameworks: Remotion, Motion Canvas, Revideo, Manim (CE/GL), Theatre.js, GSAP, Lottie/dotLottie, Rive. Strengths, look, determinism, audio sync, word-level captions, CPU speed

### Takeaway
Remotion (React, v4.0.5xx line, v5.0 staged but not confirmed released) is the most complete and best-documented option for this job: frame-addressed deterministic rendering, first-party word-level caption tooling, Three.js/WebGPU canvases, official LLM agent skills, and it is free for individuals and companies of up to 3 people. GSAP (now 100% free including SplitText/MorphSVG/DrawSVG) is the best "motion vocabulary" library and can be driven frame-by-frame inside Remotion or HyperFrames. Manim CE is the best for mathematically precise, "3Blue1Brown-look" diagrams and is the dominant target of LLM-agent research, but it is slower and its look is narrower. Motion Canvas has slowed (last stable Dec 2024); its fork Revideo is still shipping (0.11.0, July 2026). Theatre.js's public development has been paused since Aug 2024.

### Inferences
- Determinism model (UNVERIFIED general knowledge, consistent with the docs above): Remotion renders each frame by setting the frame and screenshotting, so anything derived from `useCurrentFrame()`/`interpolate()`/`spring()` is deterministic; avoid `Math.random()`/`Date.now()`/CSS transitions/R3F `useFrame`. GSAP is deterministic if a timeline is created `paused: true` and `tl.seek(frame / fps)` is called per frame (this is how HyperFrames captures GSAP—see Q7). Lottie: `goToAndStop(frame, true)`; Rive: `advance(1/30)` per frame; Theatre.js: set `sequence.position`; Motion Canvas/Revideo/Manim are deterministic by construction (generator/timeline playback).
- Audio sync: Remotion and Revideo treat audio as a first-class track and expose ms→frame conversion; Motion Canvas has an audio track and editable "time events" for voice-over sync; Manim needs a plugin (e.g. manim-voiceover, UNVERIFIED this session) or manual `add_sound` + timings. For a narrated 90 s piece, drive every animation cue from the word-timestamp JSON (see Q6) rather than hand-tuned frame numbers.
- "Typical look": Remotion/HyperFrames = anything the web can render (CSS typography, SVG, canvas, WebGL) → closest to agency motion design; Motion Canvas/Revideo = crisp vector, code-editor-tutorial look; Manim = black-background mathematical diagrams with LaTeX/Typst, morphing shapes (easy to look "academic", needs styling work for a consumer explainer); Lottie/Rive = designer-authored vector assets (icons, character loops) imported as layers.
- CPU speed ranking for 2D content (UNVERIFIED, relative): Lottie/dotLottie software raster ≈ Rive ≈ simple DOM/SVG in Remotion > Motion Canvas/Revideo canvas > Manim Cairo (Python per-mobject rasterization is slow for dense scenes) > anything with CSS blur/shadows or WebGL under SwiftShader.
- Recommendation for this project: Remotion 4.x (free licence applies if the producer is an individual or ≤3-person team) as the compositor/timeline; GSAP (SplitText, DrawSVG, MorphSVG) inside it for typographic and SVG motion; D3 for scales/path generation; `@remotion/three` only for the 1–3 short 3D shots; pre-rendered PNG/MP4 layers (Mol* stills, Blender or Three.js passes) imported as `<Img>`/`<OffthreadVideo>`. Avoid Theatre.js (paused) and Motion Canvas (stalled) for new work.
- Remotion needs a Chrome Headless Shell; Remotion normally downloads its own (source host UNVERIFIED—believed to be Google's Chrome-for-Testing CDN, not GitHub). If blocked, point Remotion at Playwright's Chromium via the `browserExecutable` option (UNVERIFIED flag name for current version).

## Q2. 3D in the browser for video (Three.js/R3F, WebGPU in headless Chromium, SwiftShader, post-processing, particles, SDF/raymarching, Gaussian splats) and Blender headless on CPU

### Takeaway
Three.js/R3F under headless Chromium renders correctly on SwiftShader (CPU), and WebGPU can be enabled as "software only" via SwiftShader-Vulkan flags, but every fragment-heavy effect (bloom, DoF, volumetrics, raymarched SDFs, large splat clouds) costs CPU time proportional to 2.07 MP/frame at 1080×1920. Keep 3D shots short, lower internal resolution for expensive passes, and prefer WebGL2 paths. Blender is now pip-installable (`bpy` 5.3.0 wheel for CPython 3.13 on manylinux x86_64, from PyPI, not GitHub), making Cycles-CPU feasible for a few short hero shots if budgeted in hours, not minutes.

### Cited Findings
- SwiftShader is an open-source CPU implementation of Vulkan and OpenGL ES; Chromium calls it "a high security risk due to JIT-ed code running in Chromium's GPU process"; WebGL fallback remains supported by opt-in, not for untrusted content — [Chromium: Using Chromium with SwiftShader](https://chromium.googlesource.com/chromium/src/+/798e59c5275d4131797e8ea2e96e6c6000256b58/docs/gpu/swiftshader.md)
- Headless Chrome ships with GPU disabled; Chrome's own guide enables WebGPU on Linux with `--headless=new --use-angle=vulkan --enable-features=Vulkan --disable-vulkan-surface --enable-unsafe-webgpu`; on a GPU-less host the WebGPU status becomes "software only" with renderer "ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)…), SwiftShader driver-5.0.0)" — [Chrome for Developers: Supercharge Web AI model testing](https://developer.chrome.com/blog/supercharge-web-ai-testing). (Older article; Playwright passes the same `args` to `chromium.launch()`—not verified against current Playwright docs.)
- Three.js `WebGPURenderer` "automatically falls back to WebGL 2 if WebGPU isn't available", but WebGPU-only features (e.g., compute) must be avoided if relying on the fallback — [three.js forum: TSL and webgl2 vs webgpu](https://discourse.threejs.org/t/tsl-and-webgl2-vs-webgpu/87974); TSL compiles to WGSL and GLSL — same thread.
- `EffectComposer` and its passes "are not supported with WebGPURenderer"; post-processing must use the TSL node stack — [three.js manual: Post-Processing with WebGPURenderer](https://threejs.org/manual/en/webgpu-postprocessing). Community docs show bloom via `three/addons/tsl/display/BloomNode.js` (threshold/strength/radius); a 2026 skill reference says `RenderPipeline` replaced `PostProcessing` in r183 while other guides still use `PostProcessing` — version-sensitive, verify against pinned release — [three.js WebGPU post-processing thread](https://discourse.threejs.org/t/three-js-webgpu-post-processing-effects/87390.md); [webgpu-threejs-tsl skill doc](https://cdn.jsdelivr.net/npm/claude-code-skills@0.5.0/data/skills/webgpu-threejs-tsl/docs/post-processing.md)
- Remotion offers `<ThreeWebGPUCanvas>` (WebGPURenderer + TSL) and requires `gl: "angle"` for Three.js — [Remotion @remotion/three](https://www.remotion.dev/docs/three); `swangle` is recommended with no GPU, "Rendering might be slow" — [Remotion gl-options](https://www.remotion.dev/docs/gl-options)
- Gaussian splats: Spark (World Labs) is "An advanced 3D Gaussian Splatting renderer for THREE.js" on WebGL2; `SplatMesh` renders alongside normal meshes in one scene; reads PLY, SPZ, SPLAT, KSPLAT, SOG; npm `@sparkjsdev/spark` — [Spark GitHub README](https://github.com/sparkjsdev/spark); [sparkjs.dev](https://sparkjs.dev/). Spark 2.0 (April 2026) added LoD + streaming for huge scenes — [World Labs: Spark 2.0](https://worldlabs.ai/blog/spark-2.0). An experimental WebGPU renderer "Spark Radix" exists — [Radiance Fields: Spark Radix](https://radiancefields.com/spark-radix-brings-webgpu-splat-rendering-to-threejs). MIT licence per one source — [radiancefields.com Spark](https://radiancefields.com/platforms/spark)
- gsplat.js (Hugging Face) is a standalone three.js-like library for splats (.ply/.splat), npm `gsplat`; Luma's `@lumaai/luma-web` provides `LumaSplatsThree` integrated with three.js tone mapping/fog; the original 3DGS research code licence is non-commercial, so splat-data provenance matters — [gsplat.js](https://github.com/huggingface/gsplat.js/); [luma-web-library](https://github.com/lumalabs/luma-web-library)
- Blender as a module: `bpy` 5.3.0 released 2026-11-10 (release history also shows 5.2.5 dated 2026-11-24), Python `==3.13.*` only, Linux wheel `bpy-5.3.0-cp313-cp313-manylinux_2_28_x86_64.whl` = 427.5 MB — [PyPI bpy](https://pypi.org/project/bpy/). Older versions are removed from PyPI but kept at download.blender.org/pypi/bpy/ — [PyPI bpy 5.0.0 / search summary](https://pypi.org/project/bpy/5.0.0/). Using bpy is "equivalent to running a script in background-mode" — [Blender API: Blender as a Python Module](https://docs.blender.org/api/5.3/info_advanced_blender_as_bpy.html)
- For headless servers without GPU, the community `bpy-widget` package recommends Cycles with device CPU — [PyPI bpy-widget](https://pypi.org/project/bpy-widget/)
- Blender CPU rendering performance has been "largely flat" across versions 3.0→5.0 — [Phoronix, Dec 2025](https://phoronix.com/news/Blender-5.0-Benchmarks-To-3.0); standard CPU benchmark scene is BMW27 — [OpenBenchmarking pts/blender](https://openbenchmarking.org/test/pts/blender&eval=d0ebc14de67e79ac23e6c8ae9d861d490d86885d)

### Inferences
- SwiftShader feasibility tiers (UNVERIFIED estimates for 4 cores at 1080×1920, must be benchmarked): (a) unlit/flat or MeshStandard scene with a few thousand triangles: roughly 0.2–1 s/frame; (b) + TSL/UnrealBloom (multi-mip blur chain) and FXAA/SMAA: roughly 0.5–3 s/frame; (c) full-screen raymarched SDF or volumetric (64–128 steps/pixel): several to tens of s/frame → render at 540×960 (or lower) and upscale, or bake to video once; (d) Gaussian splats: GPU sorting is emulated on CPU; 100k–500k splats likely seconds/frame. A 5 s 3D shot (150 frames) in tier (b) ≈ 1–8 min — acceptable.
- Prefer WebGL2 (`WebGLRenderer` + pmndrs `postprocessing` or three's EffectComposer) over WebGPU-on-SwiftShader-Vulkan for reliability; WebGPU in this environment is a "software only" adapter behind an unsafe flag and adds risk without speed benefit (inference).
- Cheap "premium 3D" looks that survive CPU rendering: baked lighting/matcaps (MeshMatcapMaterial) for a glossy enamel look, fresnel rim shaders for "x-ray" tooth/receptor, additive-blended point sprites for particle "pain signal" flows (CPU-simulated positions computed from frame number, so deterministic), fake volumetric god-rays via a few stacked additive planes, and pre-blurred background plates instead of real DoF.
- Blender path: `uv pip install bpy==5.3.0` under Python 3.13 (wheel on PyPI, no GitHub dependency). EEVEE requires an OpenGL context/GPU; whether EEVEE/Workbench can run via Mesa llvmpipe in this container is UNVERIFIED—plan on Cycles CPU. Rough budget (UNVERIFIED): a simple tooth model with glass/SSS-like enamel, 32–64 samples + OpenImageDenoise at 1080×1920 on 4 cores ≈ 15–90 s/frame → a 4 s shot (120 frames) ≈ 0.5–3 h. Mitigations: render at 15 fps and frame-blend/interpolate, render at 50–75% resolution then upscale, use adaptive sampling + denoise, keep camera moves slow so fewer samples look clean, or render a 360° turntable once and reuse.
- Gaussian splats are low priority for this script: there is no evident open-licensed splat of a tooth or receptor; they are useful mainly for photoreal environment plates.

## Q3. Molecular visualization from code (Mol*, 3Dmol.js, NGL, ChimeraX/OSMesa): rendering PDB structures (MOR 4DKL/8EF5, naloxone) into animation frames on CPU; licensing

### Takeaway
Mol* (MIT) is the strongest choice: it has a DOM-less `HeadlessPluginContext` for Node (needs the native `gl` package) and, more robustly for this container, can be run in Playwright Chromium on SwiftShader WebGL with per-frame camera/representation control and screenshots. 3Dmol.js (BSD) is the simplest to script in-page. ChimeraX can render offscreen on Linux via bundled OSMesa (CPU) but its licence and download flow are less automation-friendly. For the mechanism scene, a 2025 cryo-EM series of naloxone-bound MOR (PDB 9PXU–9PXY) now exists, alongside 4DKL (antagonist-bound mouse MOR) and 8EF5 (fentanyl-bound human MOR–Gi).

### Cited Findings
- Mol* provides a `HeadlessPluginContext` "that can be used in Node.js (without DOM)" with a `HeadlessScreenshotHelper`; requires the `gl` package (optional `pngjs`, `jpeg-js`) installed separately (`npm install --no-save gl jpeg-js pngjs`); example `node lib/commonjs/examples/image-renderer 1cbs ../outputs_1cbs/`; an `mvs-render` example renders MolViewSpec files; labels are skipped in Node because `document` is unavailable — [Mol* headless-plugin-context (mirror)](https://git.enzim.ttk.hu/web/TmMolStar/src/a678893bdbc1ff81cba92c9cc30edd606df7983d/src/mol-plugin/headless-plugin-context.ts); [Mol* mvs-render example (mirror)](https://git.enzim.ttk.hu/web/TmMolStar/src/c592a3b93d915b10a006924e387901880c03d099/src/examples/mvs/mvs-render.ts?lang=gl-ES); [Mol* image-renderer example (mirror)](https://git.enzim.ttk.hu/web/TmMolStar/src/de46f08bf495fb2533c571ab875666d025a374f8/src/examples/image-renderer/index.ts)
- An alternative wrapper (MoleculeKit) avoids `gl` by starting a singleton Chromium and driving Mol* over the DevTools protocol — [MoleculeKit molstar.render docs](https://software.acellera.com/moleculekit/reference/moleculekit.viewer.molstar.render.html)
- Mol* is MIT-licensed, built on NGL and LiteMol, developed by RCSB PDB and PDBe — [Wikipedia: Mol*](https://en.wikipedia.org/wiki/Mol*). 3Dmol.js is "distributed under the permissive BSD open source license" — [3Dmol.js paper (PMC)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC4393526/)
- ChimeraX offscreen rendering is Linux-only, using OSMesa "included in Linux ChimeraX"; OSMesa "does not use graphics hardware acceleration, only the CPU so it will be much slower"; in nogui mode the default simulated window is 256×256 (set image size explicitly) — [ChimeraX users mailing list](https://mail.cgl.ucsf.edu/mailman/archives/list/chimerax-users@cgl.ucsf.edu/message/FMIKJIEHWYHDQWGOEU235GROLD2A5ZOP/)
- PDB 4DKL: "Crystal structure of the mu-opioid receptor bound to a morphinan antagonist" (β-FNA, ligand BF0), mouse MOR–T4 lysozyme fusion, X-ray 2.8 Å, released 2012-03-21, Manglik et al., Nature 485:321 — [RCSB 4DKL](https://www.rcsb.org/structure/4DKL)
- PDB 8EF5: "Fentanyl-bound mu-opioid receptor-Gi complex", human MOR, cryo-EM 3.30 Å, released 2022-11-09, Zhuang et al., Cell 185:4361 — [RCSB 8EF5](https://www.rcsb.org/structure/8EF5)
- Naloxone-bound MOR: PDB 9PXU (inactive naloxone–MOR–nanobody, 3.40 Å), 9PXV (naloxone–MOR–Gi1 nucleotide-free, 3.02 Å), 9PXX, 9PXY, 9PXW (latent state, 3.8 Å); Khan et al., Nature 648:755–763 (2025); naloxone holds MOR in a "latent" state while loperamide favours an "engaged" state; released 2025-11-12 — [RCSB 9PXU](https://rcsb.org/structure/9PXU); [IBDC 9PXV](https://ibdc.dbtindia.gov.in/isda/summary/9PXV); [PDBj 9PXW](https://pdbj.org/mine/summary/9pxw)

### Inferences
- Most robust CPU pipeline (inference): load Mol* (npm `molstar`) in a page inside Playwright Chromium (SwiftShader WebGL), fetch mmCIF from RCSB (files.rcsb.org, not GitHub), script representations (cartoon receptor in a muted colour, ball-and-stick/spacefill ligand with emissive highlight, transparent molecular surface for the pocket), set camera per frame from a deterministic keyframe function, call the canvas screenshot per frame, and encode with ffmpeg; or export a transparent PNG sequence and composite in Remotion. This sidesteps `gl` native builds. The `gl` npm package typically fetches prebuilt binaries from GitHub releases (UNVERIFIED), which are blocked here, forcing a source build (needs build tools and Mesa/X11 dev headers).
- Simpler story-telling alternative: render only a handful of high-quality Mol* stills (e.g., receptor overview, pocket close-up with agonist, pocket with naloxone) and animate them in 2.5D in Remotion (parallax, zoom, crossfade, ligand-swap via masked dissolve). Per-frame molecular renders at 1080×1920 with SSAO/outlines on SwiftShader are likely ~0.5–3 s/frame (UNVERIFIED estimate), so a 5 s rotating shot ≈ 1–8 min—affordable.

## Q5. Data-visualization animation best practice in code (D3 transitions, icon arrays, number tickers, chart morphs, Flourish/Datawrapper-style reveals, explorable-explanation/scrollytelling vocabulary adapted to video)

### Takeaway
The best evidence base is still Heer & Robertson's work on animated transitions: animate between chart states with simple, staged transitions that keep the graphic valid and the encoding consistent, "as long as needed, but no longer." In video, the scrollytelling "step" becomes a narration beat: one data change per beat, synced to the spoken word, with persistent axes and in-place annotation.

### Cited Findings
- Heer & Robertson (InfoVis 2007) studied animated transitions between bar, pie and scatter charts; two controlled experiments found "animated transitions can significantly improve graphical perception" — [UW IDL: Animated Transitions in Statistical Data Graphics](https://idl.uw.edu/papers/animated-transitions); [paper PDF](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)
- Derived design principles taught from that work: "Use simple transitions", "Use staging for complex transitions", "Make transitions as long as needed, but no longer", keep data graphics valid during transitions, use consistent mappings — [UW CSE442 Animation lecture](https://courses.cs.washington.edu/courses/cse442/24au/lectures/CSE442-Animation.pdf)
- Follow-up evaluation found benefits for both object-tracking and value-estimation tasks; Kim & Heer's Gemini/Gemini2 generate staged keyframe sequences between statistical graphics — [par.nsf.gov follow-up](https://par.nsf.gov/servlets/purl/10172013); [Automating Animated Transitions in Statistical Graphics](https://digital.lib.washington.edu/researchworks/items/d8583a34-280a-4902-a9e4-9c8cb2769368/full)
- GPU-dependent CSS effects (blur, shadows, gradients) slow rendering in GPU-less environments; precompute them as images — [Remotion Performance](https://www.remotion.dev/docs/performance)

### Inferences
- 81% → 40% → 11% pain prevalence (inference): use a 10×10 icon array (100 tooth or person glyphs) that is state-continuous—the same 100 glyphs recolour/fade from "pain" to "no pain" between stages (object constancy), with a big tabular-numeral number ticker (interpolated with an ease-out, rounded per frame, `font-variant-numeric: tabular-nums` to avoid jitter) and a timeline label ("pre-op → 24 h → 7 d" or whatever the source study's time points are). Stage each step: (1) highlight cohort, (2) colour change, (3) number lands, (4) annotation.
- NSAIDs-vs-placebo time course: line chart whose paths draw on with stroke-dashoffset (GSAP DrawSVG) synced to the narration, placebo line first (it is the story), then NSAID line, then a shaded "difference" band; keep axes fixed across the whole scene; label lines directly at their ends rather than with a legend (Datawrapper-style direct labelling).
- Odds ratios: forest-plot vocabulary—point estimate square scaled by weight, CI whisker drawing outward from the point, vertical OR = 1 reference line drawn first, log-scaled x-axis (D3 `scaleLog`), "favours placebo / favours drug" captions; reveal studies top-to-bottom, then the pooled diamond with a small overshoot ease.
- Flourish/Datawrapper-style reveals = bars grow from the baseline with staggered delays (~40–80 ms), value labels count up and ride with the bar end, gridlines fade in before data, colour reserved for the focal series and grey for context. Chart morphs (bar → icon array, or line → single highlighted point) should use D3 `interpolate` on positions/paths (or MorphSVG for shapes) with intermediate staging rather than simultaneous all-attribute tweens.
- D3 in a frame-based renderer: compute scales/paths with D3 but do NOT use `d3-transition` timers (they are wall-clock based); instead compute `t = interpolate(frame, [start, end], [0, 1], easing)` and apply D3 interpolators directly—this keeps renders deterministic (UNVERIFIED as documented practice, but follows from Remotion's frame model).
- 9:16 layout: charts should occupy the middle ~60% of height to stay clear of platform UI (top status/title, bottom captions/CTA), with minimum 40–48 px type for axis labels at 1080 width (practitioner heuristic, UNVERIFIED).

- No primary sources were fetched on Flourish/Datawrapper animation defaults, icon-array comprehension research (e.g., risk-communication literature), or number-ticker perception; these are practitioner conventions in the notes above.
- The original figures/time points for the 81%→40%→11% data and the OR values are out of scope for this note.

## Q8. Visual-quality tricks that make code-rendered video look premium (motion blur via sub-frame accumulation, easing, DoF fakes, grain/film look, 2.5D parallax, sound-design cues), with CPU render-time estimates

### Takeaway
The premium look comes mostly from motion craft (easing, staging, overlap, motion blur) and finishing (grain, subtle vignette, colour grade, sound design), not from heavy real-time effects. On a CPU-only box, implement blur/DoF/glow as pre-rendered or ffmpeg-stage effects, use sub-frame accumulation only on fast moves, and budget: a 2D-heavy 90 s piece should render in minutes; short WebGL shots in minutes each; Cycles hero shots in hours.

### Cited Findings
- Remotion motion blur: `<HtmlInCanvasMotionBlur>` is the recommended implementation—`shutterAngle` sets exposure as a fraction of a frame and `samples` sets how many snapshots are blended ("more samples give a smoother blur but add rendering work"); `<CameraMotionBlur>` is "not recommended anymore" (colours/opacity can be inaccurate); `<Trail>` draws earlier positions without blending; built-in transitions have an optimised `motionBlur` prop; motion blur is "expensive" — [Remotion Motion Blur](https://www.remotion.dev/docs/motion-blur)
- HTML-in-canvas features require Chrome 149+ with `chrome://flags/#canvas-draw-element` for preview, while rendering "needs no configuration"; the API is unstable and Chrome may change it — [Remotion HTML-in-canvas](https://www.remotion.dev/docs/html-in-canvas); [Remotion motion blur guide](https://www.remotion.dev/docs/motion-blur-guide); [Chrome: HTML-in-canvas origin trial](https://developer.chrome.com/blog/html-in-canvas-origin-trial)
- CSS blur, drop-shadow, box/text-shadow, gradients are GPU-dependent and become bottlenecks without a GPU—replace with precomputed images; JPEG intermediate frames are faster than PNG — [Remotion Performance](https://www.remotion.dev/docs/performance)
- Headless Chromium without GPU = "significant slowdown"; `swangle` "Rendering might be slow"; `angle` leaks memory on long renders → split into parts — [Remotion GPU](https://www.remotion.dev/docs/gpu); [Remotion gl-options](https://www.remotion.dev/docs/gl-options)
- Transition timing: "Make transitions as long as needed, but no longer"; stage complex transitions — [UW CSE442 Animation](https://courses.cs.washington.edu/courses/cse442/24au/lectures/CSE442-Animation.pdf)
- Manim renderer speed anecdote: a 2026 third-party blog reports 278.83 s (Cairo-style) vs 35.28 s (OpenGL) on its own benchmark—single unverified source — [explainx.ai ManimGX blog](https://explainx.ai/blog/manimgx-agent-animation-engine-rust-gpu-guide-2026)

### Inferences
**Techniques (practitioner knowledge, UNVERIFIED in this session unless cited above)**
- Easing: never linear for UI-like motion; use expo/quint-out for entrances, in-out cubic for camera moves, springs (Remotion `spring()` with damping ~12–20, no visible overshoot for medical tone) for pops; offset related elements by 2–4 frames (overlapping action) so groups feel choreographed.
- Motion blur on CPU: if `HtmlInCanvasMotionBlur` is unavailable in Playwright's Chromium version (needs ≥149), do manual sub-frame accumulation: render the fast segment at N× fps (e.g., 8 sub-frames/frame for a 180° shutter → sample the first half of each frame interval) and average with ffmpeg (`tmix=frames=N` then `select`/`framestep`), or apply blur only to the moving layer. Cost scales ~linearly with N, so restrict to whip-pans, swipes, and fast data transitions (~5–10% of runtime).
- Depth-of-field fakes: render foreground/mid/background as separate layers; pre-blur the out-of-focus layers once (ffmpeg `gblur` or Sharp/ImageMagick on still plates) instead of CSS `filter: blur()` per frame; animate focus pulls by crossfading between sharp and pre-blurred versions.
- 2.5D parallax: place flat SVG/PNG layers at different z (CSS `perspective` + `translateZ`, or Three.js planes with an orthographic→perspective camera), drive a slow dolly/arc camera; 3–5 layers is enough. Works well for the tooth cross-section (bone, PDL, root, pulp as layers) and for Mol* stills.
- Film look/finishing in ffmpeg (cheap, post-render): subtle grain (`noise=alls=6:allf=t` or overlay a pre-rendered grain plate at 5–10% opacity in soft-light), gentle vignette (`vignette`), mild LUT grade (`lut3d`), and a 1–2 px chromatic offset only on transitions. Add grain after scaling, before final encode; encode with x264 `-crf 16–18 -preset slow -tune film` or `-tune animation` for flat graphics, `yuv420p`, `+faststart`; slightly higher bitrate prevents grain from turning into banding/blocks on social re-encode.
- Gradients/banding: dither large dark gradients (grain helps) and render in 8-bit sRGB with no CSS `filter`.
- Sound-design cues: whoosh on camera moves/whip transitions, soft ticks synced to number-ticker digit changes (throttled), low "thump" on statistic landings, riser before the reveal of 11%, and a muted heartbeat/pulse under the pain-signal section; duck music −8 to −12 dB under narration; place SFX 1–2 frames before the visual hit. All cue times can be generated from the same word-timestamp JSON and mixed with ffmpeg `amix`/`adelay` or Remotion `<Audio>`.

**Render-time budget for this container (order-of-magnitude estimates, UNVERIFIED—benchmark first)**
- 2D Remotion (DOM/SVG/GSAP, no CSS blur/shadows), 1080×1920, JPEG intermediates, concurrency 3–4: roughly 5–20 frames/s aggregate → 2,700 frames ≈ 2–10 min. With heavy CSS blur/shadow/gradient filters under SwiftShader, this can fall several-fold (≈15–45 min).
- Sub-frame motion blur on ~10% of frames at 8 samples ≈ +70% total 2D render time.
- Three.js/R3F shots via `swangle`/`angle` (SwiftShader): ~0.2–3 s/frame depending on post-processing → a 5 s shot (150 frames) ≈ 1–8 min; raymarched/volumetric full-screen shaders: render at half resolution or bake.
- Mol* per-frame renders in Chromium: ~0.5–3 s/frame → 150 frames ≈ 1–8 min; stills + 2.5D animation ≈ seconds.
- Manim CE (Cairo) 1080×1920: simple scenes seconds-to-minutes per 10 s; dense scenes (hundreds of mobjects, LaTeX) much slower; LaTeX can be avoided with the `typst` extra or plain `Text`.
- Blender Cycles CPU (bpy 5.3, 4 cores) for 1–3 hero shots of 3–5 s: ~15–90 s/frame → 0.5–3 h per shot; acceptable only if done once and cached.
- ffmpeg finishing pass (grain, vignette, LUT, x264 slow) on 90 s 1080×1920: a few minutes on 4 cores.
- Memory: keep Chromium concurrency ≤3–4 with 15 GB RAM; split long `angle` renders into chunks (e.g., 300-frame ranges) and concat with ffmpeg to avoid the documented leak.

### Gaps

- Whether Playwright's bundled Chromium version in this container is ≥149 (needed for HTML-in-canvas motion blur) is unknown.
- No controlled studies were found linking grain, motion blur, or SFX density to viewer engagement for medical explainers; recommendations are craft conventions.
